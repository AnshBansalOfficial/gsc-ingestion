Claude — Build an AI-Assisted Java Development POC

I need you to build a complete working Proof of Concept for an AI-assisted Java development workflow.

Context

I received an RFR through Unthinkable Solutions from GSC Company for a developer/resource focused on AI-assisted development for Java.

The broader requirement involves using AI to assist with software development by consuming application/production signals such as logs, understanding the relevant codebase, identifying the source of an issue, making the required code changes, validating those changes, and creating a Pull Request.

I need to build a small working demonstration of this concept.

This is not intended to be production-ready.

It is a POC that needs to convincingly demonstrate the core workflow end-to-end.

I have approximately one day, so keep the implementation simple and reliable.

Do not build unnecessary enterprise infrastructure.

What I want to demonstrate

The core concept is:

Application
    ↓
CloudWatch Logs
    ↓
Log Classification
    ↓
Alert / Error
    ↓
AI Coding Agent
    ↓
Codebase Understanding
    ↓
Code Modification
    ↓
Testing
    ↓
GitHub Pull Request

The important thing is that this should be a real working pipeline, not a mocked demo.

Demo Application

Create a very small Java application.

The application exists primarily to generate logs for the demonstration.

It should have a very simple frontend/interface with actions such as:

[ Send Alert ]

[ Simulate Error ]

When the user triggers an alert, the Java application should produce an alert/warning-type log.

When the user triggers an error, the Java application should produce an error that is intentionally introduced for the purpose of the POC.

The application itself should remain extremely simple.

There is no need to create a complicated business domain.

The actual bug/error can be trivial.

The point is not to demonstrate complex Java logic.

The point is to demonstrate what happens after an error is produced.

AWS / CloudWatch

I already have an AWS account.

The application's logs should genuinely reach AWS CloudWatch.

I want to be able to open the AWS console during the demo and show that the log was actually generated and ingested.

Design the simplest sensible architecture for:

Java Application
       ↓
CloudWatch
       ↓
Downstream processing

You decide the appropriate AWS services/mechanisms for the POC.

Prioritize simplicity.

Log Classification

The system should distinguish between different types of events.

At minimum:

Alert
Error

The purpose is to demonstrate that not every event automatically triggers an AI coding workflow.

For example:

ALERT
  ↓
Notification

ERROR
  ↓
AI coding workflow

The classification does not need to use an LLM.

Use whatever simple and reliable mechanism makes sense.

The important thing is that this classification step genuinely exists in the architecture.

For an alert:

Frontend
   ↓
Java application
   ↓
CloudWatch
   ↓
Classification
   ↓
Alert detected
   ↓
Email notification

Use an SMTP-based email mechanism for the POC.

The email should simply demonstrate that the system detected the alert.

For example:

It does not need to do anything further.

Error Workflow

This is the primary workflow.

When an error is generated:

Frontend
   ↓
Java application
   ↓
CloudWatch
   ↓
Error detected
   ↓
AI coding workflow starts

Immediately after the error is detected, send an SMTP email informing the user that the AI agent has started working on the issue.

Something conceptually like:

An application error has been detected.
The AI engineering agent is investigating the issue and preparing a Pull Request.

This email is important because the AI/code-generation process may take some time.

AI Coding Agent

The AI agent should be capable of taking the detected error and investigating the associated Java codebase.

It should be able to:

receive the relevant error information
inspect the repository
identify relevant source files
understand the relevant code
inspect relevant tests
use repository-level instructions/documentation where appropriate
determine the likely cause
make an appropriate code change
avoid unrelated modifications
run tests
create a Git branch
commit the changes
create a GitHub Pull Request

Use Claude as the LLM.

Use the appropriate Claude API/model available.

Keep model configuration flexible rather than hardcoding assumptions unnecessarily.

Codebase Understanding

An important part of this POC is demonstrating that the AI agent can understand a codebase rather than simply receiving a raw error message and guessing.

Give the repository some basic structure/documentation that the agent can use.

For example, repository instructions, source code, tests, and documentation.

The agent should retrieve the relevant context from the repository before modifying code.

I have heard about approaches involving:

knowledge graphs
code graphs
vector search
embeddings
semantic code search
repository indexing

These are relevant concepts for a larger implementation.

For this POC, however, do not build complicated infrastructure unless you genuinely believe it is necessary.

The codebase is intentionally small.

The architecture should be designed so that more sophisticated context retrieval could be introduced later.

Code Modification

The intentionally introduced error can be very simple.

I do NOT need a realistic production bug.

A simple controlled error is enough.

For example, the application could contain a deliberately introduced failure that the AI agent can identify and remove/fix.

The resulting Pull Request can therefore be small.

That's okay.

The purpose is to prove the complete workflow:

Error
 ↓
Understand
 ↓
Fix
 ↓

 ↓

The complexity of the actual bug is not the focus.

Testing

Before creating the Pull Request, the AI agent should validate its changes.

Since this is a Java project, use the project's appropriate build/test tooling.

The agent should:

Modify code
   ↓
Run tests
   ↓
If successful
   ↓
Create PR

If tests fail, the system should handle that appropriately rather than blindly creating a PR.

Keep the retry/repair mechanism simple.

GitHub

The final output must be a real GitHub Pull Request.

The agent should:

create a branch
make the changes
commit them
push the branch
create the Pull Request

The PR should contain:

a meaningful title
incident/error context
explanation of the change
test/validation information
relevant files changed

Do not fake the PR.

I want to be able to open GitHub during the demo and show the actual PR and diff.

Completion Email

Once the PR has successfully been created, send a second SMTP email.

The email should communicate that:

The AI agent has completed the investigation.
The fix has been implemented and validated.
A Pull Request has been created.

Include the actual Pull Request URL.
